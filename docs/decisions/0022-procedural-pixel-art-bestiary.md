# ADR 0022: Procedurally generated pixel-art bestiary

- Status: Accepted
- Date: 2026-11-15

## Context

ADR 0004 asked for readable illustrated enemies with restrained animation but left the technique open. The prototype
used hand-built SVG monsters, which look rough, cannot share a consistent pixel density with the pixel-art room
scenes, and have no defined animation set. The design direction (see the theme exploration boards) is chunky,
atmospheric pixel art with strong silhouettes across many themes. The game presents a first-person, forward-facing
dungeon view, so enemies are seen head-on.

## Decision

Replace the SVG monsters with pixel-art sprite sheets generated by deterministic code in `scripts/pixel-art/`, and
commit the generated PNGs and manifests under `frontend/public/art/monsters/`.

- Eleven themes ship with art: the six priority themes (Forgotten Catacombs, Sci-Fi Research Facility, 1930s Mobster
  Underworld, Sunken Kingdom, Clockwork Empire, Haunted Carnival) and five roadmap themes (Alien Jungle,
  Dreamscapes, Arctic Station, Ghost Town, Post-Apocalyptic Settlement).
- Each theme has 5 monsters and 3 bosses, 88 creatures in total.
- Every creature has `idle` (4 frames, looping), `hit` (2), `attack` (6), `special` (6) and `death` (6) animations on a
  single sheet, six columns by five rows. Monsters use 64x64 frames; bosses use 128x128 frames at the same pixel density.
- Sprites are front-facing and anchored bottom-centre so they sit on the room floor in the first-person view.
- A manifest per theme (and a root `index.json`) describes frame size, anchor, animation rows, frame counts, timing,
  impact frame, and display names for each creature's attack and special move.
- `npm run art:verify` guards the output: no stale sheets, empty or clipped frames, missing animations, or roster
  violations.

Generated, code-authored art was chosen so the whole bestiary stays stylistically consistent, is reviewable as source,
can be re-palettised or re-timed in one place, and does not require external tools or paid services.

## Consequences

- Sprites can be loaded directly with no build step; changing a creature means editing its theme file and running
  `npm run art:build`.
- The art is a strong, cohesive first pass but not final: hand-polish by an artist can replace individual sheets as
  long as the manifest layout is preserved.
- The verifier compares PNG bytes to a fresh render, so it is run locally rather than in CI until the encoder is
  confirmed stable across zlib versions.
- Not done here: wiring the sprites into the frontend (replacing the SVG monsters in `App.tsx`), mapping server
  enemy definitions to sprite ids, and per-theme room backgrounds. These are tracked in the roadmap. Player-character sprites followed in
  ADR 0024.
- Reduced-motion handling and non-animation cues from ADR 0004 still apply when the sprites are integrated.
